# Бектест: сравниваем Impermanent Loss пулов 

Суть: моделируем транзакции на исторических данных для двух вариантов таргет пула: 

- `baseline` — пул без хука, просто базовая комиссия 0.03% (бейзлайн)  
- `with_hook` — пул с нашим кастомным хуков (Динамические комиссии + afterSwap логика) 

Сравниваем итоговую стоимость активов и Impermanent Loss. 

Основа реализации:

- из [uni-v3-lp-sim](https://github.com/0xsidd/uni-v3-lp-sim) берём загрузку и последовательное воспроизведение исторических событий
- из [LVR-minimizing-dynamic-fee-hook](https://github.com/danogurtsov/LVR-minimizing-dynamic-fee-hook) берём два независимых прогона с одинаковым входом: baseline и protected 

Инструмент пишем на Rust. 

## 1. Исторические данные

Вход для инструмента:

- `start_block`
- `end_block`
- один существующий v4 `прокси пул` для получения исторического пользовательского потока
- набор reference-пулов из результата Rust-поиска
- параметры будущего target-пула: токены, `fee`, `tickSpacing`, стартовая цена, диапазон LP-позиции, начальные количества token0 и token1

Из через RPC-провайдер читаем события `PoolManager`. 
Будем использовать [Infura](https://app.infura.io/key/all-endpoints). 
Функция [eth_getLogs](https://docs.infura.io/reference/ethereum/json-rpc-methods/eth_getlogs). 
Бесплатный тариф Infura сейчас даёт 3 млн credits в сутки и доступ к archive data. Один `eth_getLogs` стоит 255 credits, то есть лимита достаточно для разработки и небольших периодов backtest. 

Для каждого reference-пула читаем события от его `Initialize` до `end_block`:

- `Initialize`
- `ModifyLiquidity`
- `Swap`

Для `proxy_pool` читаем `Swap` от `start_block` до `end_block`.

Все записи сохраняем в локальный файл и сортируем строго по:

`block_number => transaction_index => log_index`

Это повторяет подход `uni-v3-lp-sim`.

## 2. Локальный мир

Для каждого прогона разворачиваем локально:

- официальный `PoolManager` той же версии, что используется в mainnet
- mock ERC-20 для всех нужных токенов с теми же decimals.
- реальные скомпилированные смарт контракты хука и Router 
- Для каждого референс пула `PoolKey` создаём локальный `PoolKey` с mock-токенами. local mock-токены должны быть размещены так, чтобы историческая currency0 соответствовала local currency0, а историческая currency1 — local currency1 (иначе придется инвертировать транзакции)ю 

После выполняем **Prewarm**: 

До `start_block` по очереди воспроизводим исторические `Initialize`, `ModifyLiquidity` и `Swap` каждого reference-пула.

После каждого `Swap` сверяем локальное состояние с историческим событием:

- `sqrtPriceX96`
- tick
- active liquidity
- fee

Если хотя бы одно значение не совпало, backtest завершается ошибкой. Это подтверждает, что состояние reference-пула восстановлено корректно.

## 3. Два независимых прогона

Запускаем отдельно:

- `run_baseline()` - target-пул будет без хука (address(0))
- `run_with_hook()` - target-пул будет с кастомным хуком, который мы тоже локально задеплоим

Каждый прогон: 
- Разворачивает локальный мир (PoolManager, hook и Router). 
- заново выполняет prewarm до `start_block` 
- **Создает новый target-пул** на `start_block` (это называется Initialize). Цену ставим target_sqrtPriceX96 = proxy_sqrtPriceX96 непосредственно перед началом Replay. Далее создаем ровно одну тесторую LP-позицию через modifyLiquidity. Потом стоимость этой позиции будем измерять на End_block. 
- продолжает все транзакции до end_block 

В обоих прогонах одинакова конфигурация пула ликвидности и позиции ликвидности (liquidity-profile):  

- токены, `fee`, `tickSpacing` (конфигурация пула)
- стартовая цена, диапазон LP-позиции, начальные количества token0 и token1
- последовательность исторических событий

## 4. Replay от `start_block` до `end_block`

Объединяем события reference-пулов и прокси-пула в одну последовательность, сортируем по (block_number, transaction_index, log_index) и исполняем строго по ней. 

Для каждого исторического события reference-пула локально выполняем соответствующее действие. Так reference-пулы следуют историческому рыночному потоку. 

Для каждого `Swap` прокси пула:

- определяем направление и фактический `amount_in` по `amount0` и `amount1`
- выполняем exact-input swap с тем же направлением и `amount_in` в target-пуле
- в baseline после swap дополнительных действий нет
- в with_hook вызывается реальный `afterSwap`, при необходимости запускает реальный Router через локальные reference-пулы

Все изменения Router сохраняются. После первого арбитража protected reference-пулы могут отличаться от исторических и от baseline reference-пулов. Это ожидаемо, так как with_hook-прогон моделирует мир, где наш target-пул и хук уже существовали.

## 5. Итоговые метрики

На `end_block` для каждого target-пула:

- получаем итоговые количества token0 и token1 в нашей позиции ликвидности  
- добавляем средства, которые по логике хука принадлежат LP: комиссии и MEV

**LP_value_end** — стоимость итоговых количеств token0 и token1 по внешней цене на  end_block 
**HOLD_value_end** — стоимость исходных количеств token0 и token1 по той же внешней цене на end_block 
То есть, курс конвертации каждого токена в ETH берем по состоянию на `end_block`

Выводим две отдельные метрики: 

- чистый IL от изменения состава LP-позиции: `IL = LP_value_end / HOLD_value_end − 1`
- итоговый результат LP относительно HOLD с комиссиями и доходом от MEV 

Вторая метрика отвечает на вопрос, улучшает ли hook результат LP.

## Заметки 

- Прокси пул не может быть reference пулом
