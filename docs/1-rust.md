# Rust CLI: поиск арбитражных циклов Uniswap v4 

**Цель**: Находить потенциально прибыльные арбитражные маршруты (циклы) для заданной пары токенов. 

Поиск будет происходить оффчейн. Rust ничего не деплоит, а действует на основании уже существущих пулов на форке блокчейна. 

Используем только экосистему Uniswap V4, без внешних DEX. 

Основной референс — [pawurb/univ3-revm-arbitrage](https://github.com/pawurb/univ3-revm-arbitrage).

Его `revm_arbitrage.rs` делает нужную нам базовую вещь: на локальном состоянии сети перебирает размеры входа, выполняет последовательные квоты и считает прибыль цикла из двух пулов. 
Из `univ3-revm-arbitrage` переиспользуем устройство Rust-слоя RPC, REVM и кэша состояния. Его ABI, адреса пулов и v3-математику не используем.

Что меняем:
- вместо двух жёстко заданных v3-пулов используем v4-пулы. 
- вместо v3-квотера Rust вызывает официальный [V4Quoter](https://github.com/Uniswap/v4-periphery/blob/main/src/lens/V4Quoter.sol)
- Добавляем возможность циклов из 3-х пулов (а не только двух). 

## 1. Вход CLI

### Сеть и состояние

- `chain_id = 1` — только Ethereum Mainnet в v1
- `pool_manager` — адрес официального Uniswap v4 `PoolManager` в Mainnet
- `analysis_block` — номер блока, который форкаем. 
- `v4_quoter` — адрес развёрнутого официального `V4Quoter` для этого `PoolManager`

`analysis_block` нужен, чтобы повторный запуск с тем же конфигом должен дать тот же результат.

### Пара токенов

- `token_a`, `token_b` — адреса ERC-20 токенов
- Rust сортирует их по адресу и получает `currency0`, `currency1`

Количество токенов, fee, tick spacing и будущий hook в Rust не передаются, потому что Rust не моделирует будущий пул. 

### Ограничения поиска

- `allowed_intermediate_tokens = WETH | USDC | USDT | DAI | WBTC` — вручную заданные ERC-20, разрешённые токены, через которые может проходить цикл.  
- `min_amount_in[currency0]`, `max_amount_in[currency0]`. Это граница объемов, с которых может начинаться арбитражный цикл для token0. Нижняя граница нужна, потому что слишком маленькие транзакции просто не покроют газ. Верхняя граница нужна, потому что большие сделки съедают price impact арбитраж. 
- `min_amount_in[currency1]`, `max_amount_in[currency1]`
- `amount_grid_points = 100` - сколько значений в интервале [min_amount_in, max_amount_in] будет проверяться 
- `max_hops = 3` - максимально рассматриваем маршруты длиной 3 пула. 
- `max_variations = 64` - сколько максимально пулов одной пары токенов рассматриваем. Базово хотим рассматривать все возможные пулы, но если их будет слишком много, то разумно использовать этот параметр. Пример проекта с эвристиками для более быстрых поисков: [evm-amm-search](https://github.com/KaiCode2/evm-amm-search). 
- `route_limit = 64` - сколько максимум маршрутов проверяем (если используем этот параметр, то маршрут может быть неполным; Если найдено больше 64 пулов одной пары, сортируем их PoolId по возрастанию и оставляет первые 64). 
- `final_routes = 5` - сколько самых прибыльных маршрутов оставляем. 

## 2. Найти реальные target-пулы этой пары

В v4 пул определяется через `PoolKey = (currency0, currency1, fee, tickSpacing, hooks)`. У пула нет собственного адреса контракта, его состояние хранит общий `PoolManager`. 
Почему вообще при создании пула задается tickSpacing? LP хочет задать, чтобы его ликвидность (право использовать его токены в свопах) была активна в определенной границе цен. При выходе за эти границы LP перестает получать комиссии. tickSpacing задает, насколько точно можно конфигурировать это price range. 
tickSpacing = 1 означает: при каждом изменении цены на 0.01% будет включаться / выключаться ликвидность позиций (если через этот тик проходит граница позиции) => тратим больше газа на это, зато range ликвидности можно задавать более точно. Подходит для stable-coins.   
tickSpacing = 60 означает: меньше точность размещения ликвидности, но и меньше потенциальных пересечений границ тиков => меньше gas swap. 
Документация [Uniswap V4](https://developers.uniswap.org/docs/get-started/concepts/liquidity-providers/concentrated-liquidity)

Rust читает события `Initialize` `PoolManager` до `analysis_block` и оставляет только пулы, у которых:

- `currency0` и `currency1` совпадают с заданной парой
- `hooks = address(0)`

Каждый найденный пул — реальный target-кандидат. Rust анализирует его отдельно. Если таких пулов нет, CLI завершает работу с ошибкой. Он не подменяет их «похожим» пулом.

**Код-опора:** [mev-inspect-rs](https://github.com/flashbots/mev-inspect-rs) показывает обход исторических блоков. v4-декодера в нём нет, поэтому декодирование `Initialize` реализуем по ABI `Uniswap/v4-core`.

## 3. Найти reference-пулы

Rust снова читает `Initialize` и оставляет hookless v4-пулы, у которых обе валюты принадлежат множеству:

`{currency0, currency1} ∪ allowed_intermediate_tokens`.

Анализируем только reference-пулы без кастомных хуков, чтобы не учитывать неизвестную логику сторонних hook-контрактов. 

## 4. Построить циклы (маршруты) 

Граф строится для каждого target-кандидата отдельно.

- вершина — токен
- ребро — направление swap в конкретном пуле `PoolKey`
- у каждого пула есть два ребра: `zeroForOne = true` и `zeroForOne = false`

Rust запускает bounded DFS отдельно для двух случаев: 1) стартовый токен = `currency0` и 2) стратовый токен = `currency1`. Маршрут допустим, только если:

- возвращается в стартовый токен
- содержит ровно 2 или 3 swap
- содержит выбранный target-пул ровно один раз
- не повторяет токен
- не повторяет `PoolId` 

Примеры:

- два свопа: `USDC => WETH` в target, `WETH => USDC` в reference
- три свопа: `USDC => WETH` в target, `WETH => DAI` в reference, `DAI => USDC` в reference

Поиск прекращается после `route_limit` уникальных последовательностей `(PoolId, zeroForOne)`.

Используем [`degenbot-pathfinding`](https://docs.rs/degenbot-pathfinding/latest/degenbot_pathfinding/) как библиотеку поиска. Это готовый Rust-граф с DFS, который ищет все допустимые циклы в заданных границах глубины и поддерживает параллельные пулы одной пары. 
Нам останется добавить фильтр: выбранный target PoolId должен присутствовать ровно один раз. 

## 5. Проверить маршрут на форке блокчейна 

Для каждого цикла Rust проверяет `amount_grid_points` входных сумм между `min_amount_in` и `max_amount_in` геометрической сеткой.

Каждый маршрут проверяем через [`V4Quoter`](https://github.com/Uniswap/v4-periphery/blob/main/src/lens/V4Quoter.sol) на состоянии `analysis_block`. в V4Quoter можно передавать сразу последовательность маршрутов! 

Для каждого маршрута  Rust получает:

- `final_amount` — сколько токенов фактически получили
- `gas_estimate` - сколько газа потратили 

В цикле один и тот же пул не повторяется. Поэтому результат каждого свопа можно передавать как вход для дальнейших свопов.  

`V4Quoter` выполняет swap внутри `PoolManager.unlock` и откатывает вызов. Следовательно, ни локальный fork, ни реальная сеть не меняются.

## 6. Считаем профит каждого маршрута. 

`gross_profit = final_amount - input_amount`

`gas_cost_wei = gas_estimate * base_fee_per_gas(analysis_block)` (потом переводим WEI в исходный токен) 

`net_profit = gross_profit - gas_cost`

Для каждого маршрута сохраняем размер сделки с максимальным `net_profit`. Оставляем маршруты только с `net_profit > 0`. Затем сортируем их по `net_profit` и выбираем первые `final_routes`. ОТДЕЛЬНО ДЛЯ currency0 и currency1. То есть, всего будет 2 * `final_routes` маршрутов 

## 7. Выход

Список с конфигурацией самых прибыльных маршрутов: 

- `analysis_block`
- target `PoolKey`
- упорядоченные `PoolKey` всех пулов маршрута ликвидности 
- направления `zeroForOne`
- стартовый токен
- оптимальный `amount_in`
- `net_profit` 

Это список реально прибыльных v4-циклов на существующем рынке для выбранной пары.
