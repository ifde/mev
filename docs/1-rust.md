### Rust-инструмент поиска MEV

Краткое описание:
Делаем CLI на Rust — офлайн-инструмент для одного целевого Uniswap v4-пула. Он локально на форке блокчейна отбирает и ранжирует арбитражные маршруты (циклы), содержащие этот пул, и формирует конфигурацию самых прибыльных маршрутов, которые будут проверяться он-чейн.

Вход:
- Пара токенов `token0` / `token1` и их количество (именно пул из этих токенов мы хотим потенциально создать)

## Rust v1: поиск маршрутов для будущего Uniswap v4-пула

### Цель и граница

До деплоя LP хочет ответить на один вопрос: после каких свопов в его будущем пуле возникает арбитраж и через какие действующие **Uniswap v4**-пулы его можно забрать.

Rust CLI не деплоит пул, хук или Router и не отправляет транзакции. Он выдаёт максимум 5 маршрутов, которые затем будут внесены в Router отдельной задачей.

В v1 целевой пул — full-range и без hook. Иначе начальные `amount0`/`amount1` не описывают ликвидность: для concentrated liquidity потребуется список диапазонов тиков.

### Вход

Структура `TargetPoolConfig` хранит конфиг для запуска инструмента. 

- `chain_id = 1` (ETH mainnet), `pool_manager` - стандартный адрес на Uniswap v4
- `analysis_block` — конкретный блок, который форкаем. Нужно для воспроизводимости, чтобы повторный запуск давал тот же результат
- `currency0`, `currency1` — ERC-20 токены **целевого пула**. В v1 только ERC-20, вместо native ETH используется WETH (ERC-20 смарт контракт, представляющий ETH)
- `fee`, `tick_spacing`, `sqrt_price_x96` — параметры и стартовая цена **целевого v4-пула**
- `amount0_max`, `amount1_max` — максимум токенов LP. По ним и стартовой цене вычисляется ликвидность **целевого пула**. 
- `hooks = address(0)` — проверяем только пулы, у которых нет кастомных хуков. 

Пояснение: **целевой пул** - это тот, который мы *в будущем* будем деплоить на блокчейн. 
Rust инструмент сам его не деплоит. Параметры этого пула нужно, чтобы рассчитать ликвидность пула и результат свопа в нем. 
На форке существуют только *Reference пулы*. Rust вызывает V4Quoter (официальный смарт-контракт от Uniswap), чтобы получить результат свопа, не выполняя его (под капотом V4Quoter запускает логику PoolManager.swap, получает результат и отменяет вызов через revert). 

Структура `SearchConfig` содержит параметры для поиска арбитражных маршрутов:  

- `window_blocks` — сколько последних блоков анализировать
- `allowed_tokens = WETH | USDC | USDT | DAI | WBTC` — список токенов, через которые может проходить арбитражный цикл 
- `min_amount_in` и `max_amount_in` отдельно для token0 и token1. Это граница объемов, с которых может начинаться арбитражный цикл. Нижняя граница нужна, потому что слишком маленькие транзакции просто не покроют газ. Верхняя граница нужна, потому что большие сделки съедают price impact арбитраж. 
- `amount_grid_points = 32`: сколько значений в интервале [min_amount_in, max_amount_in] будет проверяться.  
- `max_hops = 3` максимальная длина арбитражного маршрута. 
- `max_slippage_bps = 50`, `max_reference_pools = 30`, `max_hops = 3`, `max_routes = 500`, `final_routes = 5`.


### 1. Proxy-пул: откуда берём реальные пользовательские свопы

У будущего пула нет истории. Поэтому нужен действующий v4 **proxy-пул** с той же парой токенов, `fee`, `tickSpacing` и без hook. Его `Swap`-события дают реалистичные направления и размеры пользовательских сделок. Это не история будущего пула.

1. По событиям `Initialize` `PoolManager` до `analysis_block` находим кандидатов.
2. Для каждого считаем отклонение его spot-price от `sqrt_price_x96` будущего пула и пропускную способность при impact 50 bps.
3. Берём пул с наименьшим отклонением цены. При равенстве — с большей пропускной способностью.
4. В последних `window_blocks` берём 100 `Swap` с наибольшим абсолютным изменением `sqrtPriceX96`. Их direction и input — сценарии для проверки.

**Код-опора:** [mev-inspect-rs](https://github.com/flashbots/mev-inspect-rs) — обход исторических блоков и работа с событиями. Его декодеры не поддерживают v4, поэтому ABI `Initialize` и `Swap` берём из `Uniswap/v4-core` и реализуем сами.

Это статический анализ состояния на `analysis_block`. Точное воспроизведение состояния внутри старого блока требует trace/replay и в Rust v1 не входит.

### 2. Reference-пулы: какие пулы допускаем в маршрут

Reference-пул — действующий hookless v4-пул, через который Router сможет сделать вторую или третью ногу. Обе его валюты должны входить в `{currency0, currency1} ∪ allowed_tokens`, а за `window_blocks` должен быть хотя бы один `Swap`.

Для каждого направления находим `max_input_50bps`: наибольший input с price impact не более 50 bps. Алгоритм: начать с `min_amount_in`, удваивать сумму до первого недопустимого значения или `max_amount_in`, затем сделать 32 шага бинарного поиска. Пул исключается, если в любом направлении `max_input_50bps < min_amount_in`.

Так мы проверяем не абстрактную «ликвидность», а нужное свойство: может ли пул исполнить нашу минимальную сделку без price impact выше 50 bps. Единый `probe_amount` для всех пар не используем: суммы USDC и WETH несопоставимы.

Оставляем максимум 30 пулов: сначала с большим отношением `max_input_50bps / min_amount_in` в худшем направлении, затем с большим числом `Swap`, затем по `PoolId`.

**Код-опора:** официальный [V4Quoter.sol](https://github.com/Uniswap/v4-periphery/blob/main/src/lens/V4Quoter.sol). Он симулирует swap через `PoolManager.unlock` и откатывает его, поэтому состояние форка не меняется. Rust вызывает развёрнутый Quoter через Alloy. Слой RPC и кэш состояния берём за основу из [univ3-revm-arbitrage](https://github.com/pawurb/univ3-revm-arbitrage). Его v3-квотер и v3-математику не используем.

### 3. Маршруты: какие циклы перебираем

Строим граф из target-пула и 30 reference-пулов. Вершина — токен. Ребро — одно направление swap. В v4 ребро хранит полный `PoolKey`, а не адрес отдельного пула.

DFS запускается отдельно от `currency0` и от `currency1`. Принимаем только цикл, который:

- возвращается в стартовый токен
- содержит 2 или 3 swap
- содержит target-пул ровно один раз
- не повторяет токен и `PoolId`
- входит в первые 500 уникальных последовательностей `(PoolId, zeroForOne)`.

Пример: `USDC → WETH` в reference v4, затем `WETH → USDC` в target. Трёхшаговый путь возможен только через токен из `allowed_tokens`: `USDC → WETH → DAI → USDC`.

**Код-опора:** среди просмотренных проектов нет готового v4-поиска таких циклов. Здесь нужна небольшая собственная bounded-DFS реализация. `degenbot-pathfinding` используем только как ориентир для графа и дедупликации, а не как зависимость без проверки v4-семантики.

### 4. Проверка прибыли

Для каждого из 100 сценариев proxy-свопа CLI сначала применяет тот же input к модели будущего target-пула. Затем для каждого цикла проверяет 12 сумм геометрической сетки от `min_amount_in` до `max_amount_in` и выбирает лучшую.

Существующие reference-пулы котирует `V4Quoter`. Виртуальный target-пул считает отдельная full-range v4-модель. До начала поиска она должна совпасть с `V4Quoter` на 20 заранее заданных входах для тестового full-range пула без hook.

`net_profit = final_amount - input_amount - gas_cost`. Fee уже учтён в квоте, поэтому второй раз не вычитается. Маршрут проходит дальше, если он прибыльный минимум в 3 из 100 сценариев. Выбираем 5 маршрутов с наибольшей медианной прибылью. При равенстве — с меньшим gas estimate.

**Код-опора:** `univ3-revm-arbitrage` даёт пример изолированного EVM/RPC-кэша и проверки квоты.

### Выход для Router

Для каждого из 5 маршрутов сохраняем JSON: `analysis_block`, упорядоченные `PoolKey`, направления, стартовый токен, диапазон `amount_in`, `min_net_profit`, `max_gas` и результаты 100 сценариев.

Это не команда немедленно торговать. Router перед исполнением обязан заново проверить текущую чистую прибыль и отказаться от сделки, если она ниже `min_net_profit`. Формат Solidity calldata будет описан в отдельном ТЗ Router.
